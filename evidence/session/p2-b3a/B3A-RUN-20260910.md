### The defect (instrumentation credibility — stop condition hit)

`lorieB3aDump` fires at `CloseScreen`/`ddxGiveUp` with a one-shot `dumped`
flag. In BOTH probe sessions the dump files were written at STARTUP
(05:06:16, 05:15 — before any workload) with `next_record=0`:

- `/tmp/p2b3a-probe.json`: `next_record=0, dropped=0`, records `[]`
- `/tmp/p2b3a-probe2.json`: `next_record=0, dropped=0` (verified mid-session,
  BEFORE teardown — decisive: the empty dump predates all workload)

Screen init runs MULTIPLE times per session (probe2 log: 2x `InstallProbe`;
probe1 log: 14x). Each init cycle can trigger an early empty dump that
consumes the one-shot flag, so the full-session data accumulated afterwards
is never written. SIGTERM teardown does not produce a second dump.

Consequence: every B3a session deterministically yields zero records. No
procedural workaround exists (no manual dump trigger; SIGKILL is worse;
shared-memory scraping would be unverifiable). A source change is required,
which is itself a stop condition per authorization.

### Fix direction (PROPOSED, not implemented)

Minimal options, cheapest first:
1. Skip empty dumps: in `lorieB3aDump`, return early when `next_record == 0`
   WITHOUT setting `dumped` (one-line behavior change; preserves one-shot
   semantics for real data).
2. Alternatively/additionally: dump on a dedicated trigger (e.g. SIGUSR1
   handler or explicit env-requested dump point) instead of only at close.
3. Do NOT just clear the flag per screen-init: repeated inits could then emit
   multiple partial files; keep dump-once but make it data-gated (option 1).

Any of these needs an explicit source-change review round; B3a measurement

## Holder method (truncation mechanism SOLVED — no source change needed)

Root cause of all mid-session truncations, proven by logcat forensics on
CPU-A: the X server RESETS on last-client-disconnect (stock Xorg behavior).
Each reset = CloseScreen (dump attempt) + screen re-init (InstallProbe).
Oracle-end disconnect dumped 1519 records and consumed the one-shot flag;
all 7 cells' 4200 records were then lost. Disconnect counts (1 oracle + 7
cells ≈ 8 re-inits at ~5s spacing) match InstallProbe timestamps exactly.

Additional churn source: user touches/typing on the phone during a session
(Touch Boost + Stable key events 05:55:05–15) cause surface recreation and
extra re-inits. Phone must stay untouched during sessions (S3 boundary).

Fix (methodological, zero source change): `/tmp/p_b3a_hold` — one idle X
client held connected for the whole session, so exactly ONE reset happens
(at holder shutdown), whose dump carries the full ring. Proven by CPU-A3:
5719/5719, dropped=0, only 3 startup InstallProbes.

Per-session rules (fail-closed): batch full workload + teardown in ONE
command; validate `next_record == expected`; discard + rerun on truncation.
The `~/.hermes/config.yaml` near-YOLO hardening requested mid-round could
NOT be applied by the agent (tool refuses Hermes config edits) — user must
edit directly.
