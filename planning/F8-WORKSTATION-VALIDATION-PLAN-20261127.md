2026-11-27 提案。日用基線為 Fast9+09c。第一個決策是 Hybrid 可否在可信的工作樹、可接受的資源用量下長駐。架構審查採 main `40edf91` 與 [PR #53](https://github.com/waydefu/GPU/pull/53) 的 `abe9fef`；日後實作須記錄當時批准的 SHA。各路線的證據、原審 R01–R34、雲端增補 R35–R40 及原始來源見[詳細審查](../docs/F8-WORKSTATION-ARCHITECTURE-REVIEW-20261127.md)。

## 審閱時要決定的事

- **先凍結兩項決策。** 依下列預算規則記錄可接受的資源上限，再按 Git 分流表登記允許的 checkout。缺少任一收據，長測維持待驗。
- **優化目標。** 每項候選預先選擇主要終點：完整操作牆鐘、相同延遲下釋放 CPU，或相同服務量下降低記憶體。不同終點各自呈報。

## 7.5 資源預算如何定案

先在同一裝置、同一版、相同隔離互動負載下量三個狀態：Hybrid 停用、daemon 暖機空閒、一個客戶端完成各類最大合法請求。用峰值與最小餘裕選限額。另用獨立樣本檢查這組限額；每次放大到 2/4/8 個客戶端前先核算下一階的上限。以下是預算選取規則，裝置數值須填入該次驗收單。

| 要凍結的欄位 | 計算與計量範圍 | 執行與查核 |
|---|---|---|
| 全體記憶體（MiB） | 記停用時代表性負載下最低 MemAvailable 為 A，事先議定 Android／桌面須保留的餘裕 R，另留覆蓋取樣波動與不可見配置的裕量 J。整組 Hybrid PSS 的提案上限取「審閱核准值」與 A−R−J 兩者較小值。 | 對 daemon、所有 relay、本地 worker 與子程序 PID 去重，同時取樣合計 PSS；並獨立要求實際 MemAvailable ≥ R。PSS 與 MemAvailable 不是一比一換算。另記短命 child 的覆蓋、SwapPss 及每程序 RSS。 |
| 單客戶端記憶體／工作 | 全體額度先扣共用常駐基線與固定控制開銷，再除以核准的同時客戶端數 C，作為每客戶端增量上限。用單客戶端實測決定可接受的 frame bytes、雙向佇列 bytes、在途工作數與子程序輸出；分別記 raw、selective、fallback。 | 可直接計量的 bytes/工作在配置前預留，包含拆幀、排隊、重播與輸出。共用 heap 難以逐請求歸屬，另驗單客戶端 PSS 增量及整組實測峰值。仍放不下一個合法最大請求時，降低 C 或收窄宣告支援的工作。 |
| 執行緒（個） | 先量含主執行緒的固定數 T0，再按每客戶端 relay、session、local worker、原生 worker 與允許子程序的峰值 task 數編列。全體工作額度以維持互動 p95 的最高已驗設定為限；預留完成回應、拒絕及停機所需容量。 | 單客戶端與全域兩層許可；accept 後待驗的連線也占額，spawn 前取得。用各 PID 的 Threads 加總核對；若外部子程序的執行緒數無法硬限制，須列入觀測峰值並限縮可並行的子程序。 |
| FD（個） | 分程序記暖機 FD、soft RLIMIT_NOFILE 及完成控制／清理所需保留數。每程序硬預算 ≤ soft limit 減保留數；全體預算從各 relay、daemon、子程序的 socket、pipe、檔案與 pending accept 算出，分攤每客戶端額度。 | 先驗每程序，再驗全體同時開啟的 FD 表項數；FD 編號跨 PID 不去重。把建連、拒絕與關閉中持有的 FD 算入。名額與 FD 在失敗路徑也必須歸還。 |

首輪可用靜態分配避免多個 relay 各自花掉同一份額。執行緒及 FD 各填一張預算表：固定服務用量 + 待准入／清理預留 + C × 每客戶端最高用量 ≤ 核准總數；每個程序另須符合自己的 FD 上限。每客戶端最高用量涵蓋 relay、服務端為它保留的工作及子程序。啟動器須限制同時領取份額的 relay 數；daemon 停用後仍存在的 fallback 也占份額。若部署方式無法約束獨立啟動的 relay，只能登記每程序限額，全體硬上限列為未驗，停止放大。

例如全體 PSS 預算若為 160 MiB，共用基線與控制預留共 32 MiB，C=4，則每客戶端最多分得 32 MiB 增量。實測若需要 40 MiB，依此預算最多只能核准 3 個同時客戶端。這組數字只示範算法。每輪將 A/R/J、各上限、資料來源、負責審閱者、預期超額回應及回收後基線寫入預算單；任何必要欄缺值則保留待驗。許可用盡時拒絕新增工作，已接受工作依協定完成或明確終止；不得透過自動回退再占用另一組未計量資源。

## git_ro 分流決策表

信任單位是明確登記的 checkout 根與它實際使用的 Git metadata 根。首次登記記錄來源、兩個 canonical root、允許命令與讀取期間如何排除其他寫入者。commit SHA、目錄存在及相同 UID 均不足以單獨證明穩定性。首輪建議使用專用、受控的隔離快照；同 UID 任意程序可能改寫的資料不列入此保證。

| 順序 | 條件 | 結果 |
|---|---|---|
| 1. 拒絕 | 不在明示映射、命中受保護路徑、來源不受信、符號連結或 metadata 越界；倉庫無法辨識、bare、alternates、禁止設定／參數；無法證明讀取期間資料及其來源穩定。 | 原生及自動 PRoot 路由均拒絕。回覆可辨識的原因。若需要使用該倉庫，另行建立受控輸入並重新判定。 |
| 2. 允許原生 | 已登記且讀取期間受控的非 bare checkout，工作樹與全部 metadata 均在該倉庫核准範圍內，命令、參數及環境通過既有唯讀政策。linked worktree 須另外登記 gitdir 與 commondir 且驗證完整；未具備此驗收前停用其原生路由。 | 執行原生 Git，記實際 route 與預檢時間，保留逐請求檢查。 |
| 3. 可回退 | 輸入通過同等的信任與命令限制，僅因原生路由被停用或服務在執行前不可用；本地政策可獨立驗證且有預算。 | 可在 PRoot 執行一次，記原生未執行與回退原因。政策拒絕、執行狀態不明、或本地不能保證同等限制時返回明確錯誤。 |

驗收至少含穩定的小型及大型倉庫、正常 packed/loose、已登記 worktree、未登記 repo、受保護路徑與原生服務停用。逐案記預期／實際路由、子程序是否啟動與輸出摘要。大型 fixture 依 loose 物件數分組（例如 0/1k/10k/100k），預檢及 Git 本體分開計時；結果不支持收益時可對該類可信工作預設留在 PRoot。

## 數據如何裁決

每種工作先做 A/A，再按冷、暖及熱穩態分層，至少 20 對配對操作（提案），平衡 ABBA/BAAB 順序，報分母、配對差、區間與 p50/p95。p99 使用有足夠獨立請求的長測。將總 PSS、Private_Dirty、SwapPss、FD、水位、CPU 時間與溫度同列；權限缺測欄保留未知。建議採用線為代表工作牆鐘下降至少 10%、p95 退化不超過 5%；若事先選擇 CPU 為終點，則要求 CPU 降至少 15% 並維持互動延遲。這些是新提案，與既有 7.5 關卡分開判讀。

## 其他支線的啟動條件

| 支線 | 啟動條件與第一項比較 | 停止條件 |
|---|---|---|
| CPython、原生 glibc | 先找到 7.5 後仍重要的 CPU 或長壽應用工作。CPython 固定版本、libc、allocator、編譯器，比一次一個旗標；glibc 驗單一 app 完整子程序鏈。 | 擴充 ABI、憑證或路徑語意不相容，或同品質工作未過端到端門檻。 |
| MediaCodec | 有特定影音需求，才用同一 1080p60 素材比較軟硬解；固定呈現格式，辨認 codec、SHM/inline，量 30 分鐘的首幀、PTS、掉幀及記憶體。 | 硬體路由無法確認，或畫質、幀序、持續熱態不合格。 |
| OpenCL、Vulkan、Hexagon | 同 GGUF、量化、上下文與精度比 CPU/OpenCL/Vulkan，報 prefill、decode、首 token 和桌面 p95；HTP 先確認 stock app UID 的能力。 | 需要改系統安全設定、無法核對實際後端、品質或熱穩態不合格。 |

## GPU 顯示何時可重新提案

Gate A 與 GL/VK 上屏維持 PAUSED。以下兩條任一成立，可送交審閱；重新提案與批准裝置實驗分兩步。

| 提案依據 | 應附的最低證據 | 審閱決定 |
|---|---|---|
| 新的功能需求 | 指定使用者操作、應用與版本、顯示模式及正確結果，例如指定應用在外接模式必須呈現 EGL 首幀。附 stock F8 的既有紀錄或新取得授權的隔離紀錄，能重現黑屏／錯幀，並說明現有 CPU 或既有渲染路徑為何無法滿足。 | 可就單一功能缺口立案；驗收用可見正確幀、resize／重連／buffer 重用與 fence 完成順序。功能修復不外推為桌面加速。 |
| 成本模型改變，有可量的效能機會 | 固定實際應用、解析度、幀率、輸入與熱態，附同機基線，以及能定位拷貝、等待或合成佔比的時間線。說明相對舊 X3／tiny-pixmap 測項有何差異，例如大面積、高更新率負載，或有文件可查的相容格式、modifier、匯入與 fence 契約。 | 先算扣除新增 GPU copy／同步後的上限。建議門檻為完整應用 p95 frame time 可降 ≥10%，或同呈現品質下顯示路徑 CPU 可降 ≥15% 且 p95 不退化 >5%。上限都未達就維持暫停。 |

原型需要另行批准，只在隔離顯示／實驗套件及新建證據目錄驗證。固定同一 workload 做冷暖、熱態配對，驗 frame-time 分布、可見畫面、實際 renderer、拷貝次數、fence/ownership、峰值 PSS、FD 與溫度。若證據僅有外機跑分、離屏 GL 分數或驅動版本更新，維持暫停；出現錯幀、同步錯誤、資源越額、超熱或無法重現預期收益，停止原型。Stable `:1` 與歷史凍結格不作重啟驗證。這些條件適用於顯示；MediaCodec 或推理支線單獨達標不會自動重開顯示工程。

此文件 PR 供審閱施工順序。各實作另開變更，合併、部署及重啟暫停戰線各自需獨立決定。
