# POCO F8 Ultra 工作站隔離驗證與施工計畫

2026-11-27 提案。日用基線為 Fast9+09c。第一個決策是 Hybrid 可否在可信的工作樹、可接受的資源用量下長駐。架構審查採 main `40edf91` 與 [PR #53](https://github.com/waydefu/GPU/pull/53) 的 `abe9fef`；日後實作須記錄當時批准的 SHA。各路線的證據、34 項裁決及原始來源見[詳細審查](../docs/F8-WORKSTATION-ARCHITECTURE-REVIEW-20261127.md)。

## 審閱時要決定的事

- **路徑信任範圍。** 建議首輪只允許明確映射、可信且穩定的 checkout。若需要不受信任或可被並行修改的資料，須另行審查能約束實際讀取的隔離設計。兩條執行路由均應遵守決定。
- **裝置餘裕。** 在長測前先以可代表日用的隔離工作量定下整組 relay、daemon 與子程序的峰值預算，以及要留給互動工作和 Android 的餘裕；記錄各自數值、量測方法與取樣覆蓋率。現有 RSS 漂移門檻只回答排空後的問題。
- **優化目標。** 每項候選預先選擇主要終點：完整操作牆鐘、相同延遲下釋放 CPU，或相同服務量下降低記憶體。不同終點各自呈報。

## 施工順序

| 順序 | 範圍與可審閱交付物 | 通過條件 | 停止或回退 |
|---|---|---|---|
| 1 | 建立版本與路由收據。固定六個腳本及 tracer 雜湊、PR SHA、Git/Python 版本、fixture、實際執行端、每請求結果及缺測項。使用新目錄保留原始樣本。 | 同一請求在預定路由完成；輸出符合語意 oracle。驗證所有並發請求，分開記錄拒絕、取消與正常回覆。 | 腳本身份、執行端或樣本不符則該批無效，找出差異再測。 |
| 2 | 收斂 Hybrid 資源上限。分別記選擇性 relay、raw relay、fallback 的 frame 與佇列水位，並使連線准入涵蓋 thread 建立前的階段。 | 正常輸出完整，滿載可辨識；量到每客戶端及整體的在途 bytes、thread、FD 和峰值記憶體。 | 越過預先決定的預算、取消無法收斂或遺失已接受的正常回應時，停止擴大客戶端數。 |
| 3 | 對核准的 git_ro 信任範圍驗收。取小型及大型 fixture，各備 packed 與 loose 資料；將策略預檢、Git 執行、回覆排隊分段計時。 | 正常倉庫結果符合固定 Git 對照；超出信任範圍的請求被拒絕；短 Git 的 p95、取消延遲及預掃成本可交代。 | 邊界未能保證就停用該資料範圍的路由。保留原始安全檢查。 |
| 4 | 前三項達標、#53 經批准合併後，執行 7.5 的隔離長測。用 1/2/4/8 個客戶端覆蓋慢讀、取消、逾時、半關閉、重新連線、重複啟停；記各組分母。 | 原計畫至少 1,000 ops；排空後 daemon RSS 漂移 ≤10%、FD 回暖機基線、子程序與孤兒為零、停機清理完成、原生停用時 PRoot 回退成功。另核對第 2 項的峰值預算。 | 任一條件失敗即保存失敗樣本與版本，回到可工作的 PRoot 路由。完整客戶端與 GUI 驗收分列。 |
| 5 | 對已受益的 tree/hash、fixed search 逐項試有界結果生成、減少重複走訪或既有 CLI。只在已知不可變輸入共用列舉。 | 同輸出、排序、截斷、取消與 digest。比較相同工作的 PRoot resident、native selective 與既有最佳 CLI。 | 優勢只來自少做使用者要求的工作，或高水位／尾延遲退化即停用候選。 |
| 6 | 在仍留 PRoot 的真實工作建立 Fast9 熱點圖，分開記可消除的串行牆鐘與 tracer CPU。只有熱點夠大時，才研究單一動態應用的絕對路徑 stat shim。 | 計數關閉下重現端到端收益；bind、L2S、dirfd、errno、fork/exec 與 FD reuse 的結果等同 Fast9。 | 熱點份額不足、只改善微基準或任一語意改變，即結束該候選，維持 Fast9。 |

7.5 引用[原始驗收門檻](../evidence/session/proot/STAGE7-NATIVE-HYBRID-2.0-PLAN-20261127.md)。第 2、3 項可獨立準備；兩項都通過才進長測。

## 數據如何裁決

每種工作先做 A/A，再按冷、暖及熱穩態分層，至少 20 對配對操作（提案），平衡 ABBA/BAAB 順序，報分母、配對差、區間與 p50/p95。p99 使用有足夠獨立請求的長測。將總 PSS、Private_Dirty、SwapPss、FD、水位、CPU 時間與溫度同列；權限缺測欄保留未知。建議採用線為代表工作牆鐘下降至少 10%、p95 退化不超過 5%；若事先選擇 CPU 為終點，則要求 CPU 降至少 15% 並維持互動延遲。這些是新提案，與既有 7.5 關卡分開判讀。

## 其他支線的啟動條件

| 支線 | 啟動條件與第一項比較 | 停止條件 |
|---|---|---|
| CPython、原生 glibc | 先找到 7.5 後仍重要的 CPU 或長壽應用工作。CPython 固定版本、libc、allocator、編譯器，比一次一個旗標；glibc 驗單一 app 完整子程序鏈。 | 擴充 ABI、憑證或路徑語意不相容，或同品質工作未過端到端門檻。 |
| MediaCodec | 有特定影音需求，才用同一 1080p60 素材比較軟硬解；固定呈現格式，辨認 codec、SHM/inline，量 30 分鐘的首幀、PTS、掉幀及記憶體。 | 硬體路由無法確認，或畫質、幀序、持續熱態不合格。 |
| OpenCL、Vulkan、Hexagon | 同 GGUF、量化、上下文與精度比 CPU/OpenCL/Vulkan，報 prefill、decode、首 token 和桌面 p95；HTP 先確認 stock app UID 的能力。 | 需要改系統安全設定、無法核對實際後端、品質或熱穩態不合格。 |
| 2D 與 GL/VK 上屏 | 維持暫停。只有新的真實使用場景、可量效益與另外批准才另案規劃。 | 既有凍結格不重跑；Stable `:1` 不作實驗目標。 |
